# Runner protocol

The runner protocol is the authenticated control-plane-to-runner boundary. Its compatibility and release cadence are independent from the public API and guest-agent protocol.

`contracts/runner/v1/runner.proto` is the canonical schema. Generated code and a committed descriptor set derive from it. Frozen binary fixtures cover every released message generation, and breaking-change validation compares the schema with the latest supported release.

## Connection and identity

A runner uses a short-lived enrollment credential once to obtain its stable runner identity and client certificate. Normal operation uses mutually authenticated TLS with a revocable, rotatable runner certificate. Certificate identity is authoritative; a message cannot claim a different Runner or RunnerPool. Application API keys are never accepted on this channel.

Enrollment tokens are single-use, expiry-bounded, and stored only as keyed hashes. The signed client certificate carries the stable Runner identity; the enrolled database record fixes its RunnerPool. Rotation creates an active replacement while the predecessor is `retiring`, permitting deliberate connection handover, and revocation removes either certificate independently. Every TLS handshake verifies both CA trust and current database credential state. The control-plane server certificate is configured separately and TLS 1.3 is required.

Revocation atomically changes the credential state and invalidates every active connection authenticated by that serial. Any control command claim is returned to pending delivery, and the Runner becomes offline when the revoked connection was its current connection. Checkpoint admission and every inbound, outbound, and delivery-confirmation data-plane transaction lock and recheck both connection and credential authority, so an already-established stream cannot retain Exec, File, PTY, Port, or checkpoint authority after revocation.

`secondbox-runner-identity` is the operator surface for creating enrollment tokens, signing a runner-provided CSR, rotating from a currently valid certificate, and revoking a certificate serial. It runs with the runner CA and runner-enrollment hash secret, never with an application API key. Certificate output uses create-only owner-readable files so rotation cannot overwrite the current credential before handover succeeds.

The runner dials the control-plane endpoint and maintains a versioned bidirectional gRPC stream. This outbound connection supports runners behind ordinary host firewalls and NAT. The control plane does not call an unauthenticated runner HTTP port.

The first exchange negotiates a protocol version and connection ID. Unsupported versions fail before registration or mutation. Reconnect creates a new connection ID but preserves stable Runner identity. Duplicate or reordered messages are handled by operation ID and sequence number rather than connection lifetime.

The Runner owns an explicit reconnect loop with exponential delay bounded between 250 milliseconds and 30 seconds. A transient connect, send, receive, or control-plane restart error closes only the current transport session; it does not stop or fence Runner-owned Instances. The Runner retains active Assignment and correlation summaries in memory, repeats readiness registration on the new connection, and immediately sends a heartbeat that re-advertises those summaries before consuming more commands. A successful registration resets the delay. Terminal authentication, authorization, and protocol-negotiation failures stop the Runner, as does operator context cancellation; the process composition root shuts down the compute backend only after `Run` returns.

## Registration and capacity

Registration reports:

- stable Runner and RunnerPool identity established by the certificate;
- software and runner-protocol versions;
- architecture and kernel evidence;
- verified KVM, Firecracker, jailer, cgroup, networking, storage, and cleanup capabilities;
- supported guest-protocol generations;
- verified immutable image and toolchain cache entries;
- allocatable and currently reserved vCPU, memory, disk, Instance, and operation capacity.

The runner performs prerequisite and trust validation before advertising schedulable capacity. Missing KVM, required network controls, trust anchors, storage health, or cleanup capability make it unready. The control plane treats claims as evidence for scheduling, not as authority to change a ProfileRevision.

Heartbeats carry monotonically increasing sequence numbers, connection identity, capacity, active assignment summaries, and drain state. A heartbeat is runner liveness; it is not Sandbox useful activity.

Connections and message envelopes are persisted. A reconnect supersedes the prior connection ID without changing the Runner identity. Duplicate message IDs are idempotent; a new message at an old or repeated sequence is rejected. This ordering evidence remains effective when a runner reconnects to a different control-plane replica.

## Assignments and fencing

An assignment command contains the immutable ProfileRevision requirements, exactly one runtime component reference and one toolchain component reference, exact deny-all or allow-list network policy, Sandbox and Instance IDs, generation, opaque fencing token, source checkpoint, operation deadline, and correlation IDs. Each component reference carries its catalog-resolved artifact ID, component-manifest digest, signing-key ID, architecture, guest-protocol generation, and mandatory guest features. Network destinations carry one exact domain or CIDR plus protocol and port; Runner-local DNS pin bounds and protected management addresses remain local admission inputs rather than Profile-controlled exceptions. The assignment contains no application API key or end-user identity.

The released Firecracker artifact is one signed execution bundle because the toolchain is physically embedded in its rootfs/shared-image set. Its signed top-level manifest binds two distinct component manifests: runtime and toolchain. Profile `runtimeBundleDigest` and `toolchainBundleDigest` values name those component-manifest digests rather than aliasing the top-level manifest. Runner readiness advertises both exact component identities. Admission requires both assignment references to match the locally verified component descriptors and trusted key; a missing component, mutable tag, digest/key/architecture/generation/feature substitution, duplicate runtime reference, or arbitrary pull fails before VM mutation. Guest negotiation receives the two component digests independently.

The runner validates the full assignment before acknowledgement. It returns either accepted capacity reservation or a typed startup rejection. Acceptance does not make the Instance ready. Progress events cover artifact verification, workspace materialization, network setup, Firecracker launch, guest negotiation, and readiness.

Every runner message that can mutate compute or workspace state includes assignment ID, Sandbox generation, and fencing token. The control plane rejects evidence from a superseded assignment. A runner receiving an explicit fence command stops admitting work, terminates the old Instance, releases the active materialization, and returns bounded proof. It never continues work under a newer generation by inference.

`InstanceTerminal` reports a post-ready runtime observation under the retained Assignment fence and full request, operation, Sandbox, Instance, generation, Assignment, optional Lease, and Runner correlation. Its bounded reason is only `guest_shutdown`, `resource_exhaustion`, or `internal_failure`, and it carries an immutable evidence digest rather than logs or counters. Exact replay is idempotent; changed reason, digest, time, or correlation is rejected. The event records Instance state and wakes reconciliation only. It is not release proof and cannot clear Assignment or materialization authority, advance a generation, or schedule replacement.

Checkpoint commands carry the current Assignment fence, a control-plane-selected checkpoint ID and opaque storage identity, a byte bound, a deadline, and the originating request and operation correlation. The Runner rejects incomplete or mismatched correlation, freezes guest filesystem writes, and streams ordered chunks followed by checksum, size, compatibility, and terminal evidence. Checkpoint terminal evidence is emitted before the result frame and sink failure fails the operation. No runner-local path, object-store credential, Profile secret, or workspace output appears in checkpoint evidence.

The control plane durably admits each checkpoint frame through connection identity, live credential state, message ordering, and Assignment fencing before the receiver may create a spool file, write an object, or change checkpoint authority. A successful terminal result leaves the checkpoint effect queued until immutable-object and PostgreSQL publication both finish. If publication is interrupted, the deadline path reissues the same fenced checkpoint command; reconnect replay reuses strict-offset spool and immutable-object checks, allowing the same checkpoint to finish without admitting changed bytes.

Restore is the reverse provider-neutral stream. Before delivering an Assignment that names a source checkpoint, the control plane verifies that the checkpoint is the Workspace's current published root, reads it with private object-store authority, and sends `RestoreBegin` plus strict-offset `RestoreChunk` frames under the new Assignment fence. `RestoreBegin` fixes the full request, operation, Sandbox, Instance, generation, Assignment, and Runner correlation for the stream; every later chunk is checked against the retained fence and storage identity. The Runner verifies size, SHA-256, architecture, backend, workspace format, and pinned ProfileRevision before materializing a new writable generation image. It emits payload-free terminal evidence on begin failure, stream failure, or successful end-of-object before accepting any later replay. Only after the end marker is accepted does the control plane deliver the Assignment; reconnect replays the restore idempotently before retrying that Assignment.

Scheduling first applies hard ProfileRevision requirements: RunnerPool, Firecracker backend, architecture, guest-protocol generation, prerequisites, required capabilities, health, drain barrier, and free capacity. It then ranks workspace-checkpoint locality, verified artifact-cache locality, free capacity, and stable Runner ID in that order. Assignment creation locks the Sandbox generation and candidate capacity in one serializable PostgreSQL transaction. The durable Assignment snapshots the selected capabilities and records Runner, ProfileRevision, backend kind and reference, generation, fencing token, deadlines, and retry bounds.

## Operations and streams

The connection multiplexes lifecycle commands, exec, filesystem transfer, PTY, port tunnels, logs, and evidence with globally unique operation and stream IDs. Each admitted Exec, File, and Port opening carries its durable per-operation correlation on the frame envelope: request, operation, Sandbox, Instance, generation, Assignment, optional Lease, and selected Runner IDs; the reserved PTY frame has the same correlation shape. The Runner rejects missing or inconsistent opening correlation, retains it for the operation lifetime, and returns it on output and terminal frames, including terminal replay after a connection interruption. Port ingress also compares every returned frame with the PostgreSQL-pinned session correlation before accepting credit, bytes, or terminal state. Each direction uses per-stream sequence numbers. Byte-producing streams use explicit credit frames; a sender cannot exceed granted credit. Control frames have bounded priority so cancellation and fencing cannot be starved by output.

Cancellation is an acknowledged guest-directed operation. Transport disconnect does not imply successful cancellation. On reconnect, the runner reports active operations and terminal results so the control plane can reconcile without replaying a completed mutation.

Terminal results distinguish guest outcomes from admission, fencing, guest-agent, runner, and infrastructure failures. Assignment results and rejections, Exec, File, and Port terminals, checkpoint and restore completion, natural Instance termination, fencing, host network-policy failure, and instance teardown emit the same schema-versioned Runner evidence record. Its fixed shape carries only event/outcome classifications, observation time, and request, operation, Sandbox, Instance, generation, Assignment, Lease, and Runner identifiers. Lifecycle operations omit only Lease when no Lease exists. The record type and runner-protocol `Evidence` message have no fields for credentials, fencing tokens, commands, environment values, stdin/stdout/stderr, file paths or content, checksums, network destinations, or workspace data, so those values cannot be accidentally serialized as evidence. Definitive local completion or failure emits evidence before its terminal protocol frame, and evidence sink failure is surfaced rather than silently dropping required evidence.

Operation evidence is emitted as structured audit/log data, not metrics. Metrics retain only bounded dimensions such as terminal class and do not label by any correlation identifier.

The root data-plane boundary is a PostgreSQL-authoritative durable frame relay. Admission locks the Project and Sandbox operation budgets, resolves the current ready Assignment, pins its generation and fencing token, validates an optional Lease, and atomically records the activity session plus outbound frames. Each durable Exec and File frame carries the normalized request ID, operation ID, Sandbox, Instance, generation, Assignment, optional Lease, and Runner correlation fixed at admission, so reconnect replay and terminal evidence retain the same identity. Idempotency is scoped by Project, operation, Sandbox, and key; a changed request hash conflicts. The relay claims only the next contiguous outbound frame for one authenticated Runner connection and marks delivery, session state, and accounting in one transaction after a successful stream send. Failed sends remain reclaimable on reconnect. Exact inbound duplicates are harmless; conflicting duplicates, gaps, post-terminal frames, and stale generations fail. Useful inbound frames update Sandbox activity, while HTTP result polling does not.

Deadlines and byte-limit violations move an operation to `cancelling`, enqueue a priority guest cancel, and retain active-session authority until a current-fence terminal proves the guest work stopped. Draining rejects new admission but continues accepting ordered output and terminal proof for work admitted under the current Assignment. A generation fence terminalizes every remaining generation-bound relay session before replacement. Completed payloads and idempotency results remain available for the configured retention window, after which the sweeper removes their relay frames and session rows.

The Runner translates Exec, PTY, and File frames to its retained assignment-bound guest protocol session. Generation 1 supports buffered and live-streaming shell and argv execution with binary stdin plus read, write, stat, direct-child list, exists, mkdir, and remove. Streaming stdin bytes and their explicit `end_of_input` signal, output credit, and cancellation are forwarded in sequence while the guest process is running. A PTY operation opens through `ExecOpen` with `allocate_pty`, then shares one incoming sequence across PTY input, resize, and credit plus Exec cancellation. The Runner emits only typed `PtyFrame` output and terminal messages for that operation, including admission and fencing failures, so replay never changes frame kind. PTY output is chunked at the runner relay bound and stays binary through the guest, Runner, PostgreSQL relay, and public base64 envelope.

The durable relay treats an exact retransmission of the same EOF sequence as idempotent, records stdin closure atomically with that frame, and rejects every later stdin frame. Guest stdout and stderr flow back immediately when credit is available; unused credit remains available for later writes, so a slow client applies backpressure at the guest without accumulating unbounded output at either relay. Bounded partial output is preserved before an `output_exhausted` terminal. Exec and PTY terminals preserve the public outcome evidence: exit code and signal, spawn-failure reason and message, elapsed deadline, exhausted byte limit, or typed infrastructure reason and retryability. Binary file content remains bytes end to end. File operations preserve the caller's recursive and force flags, while stat and list return complete kind, size, and modification-time metadata. Runner-protocol generation 1 creates new files with mode `0600`; the guest still verifies the declared size and checksum and commits atomically.

Completed operation state is retained only in a bounded 256-entry tombstone window per operation kind for immediate duplicate terminal replay. Total active plus retained state is capped at 1024 Exec and 1024 File operations; new admission receives a typed capacity failure when the bound is exhausted. A connection loss cancels active guest work, while durable root evidence determines whether a completed frame must be reclaimed after reconnect.

## Draining and loss

Operator drain prevents new assignments and new operation admission. Existing assignments follow their profile drain bounds. A drained Runner remains connected until it has released or explicitly failed every assignment.

Heartbeat expiry marks the Runner unavailable but does not by itself authorize immediate workspace reassignment. Recovery follows [Recovery and reconciliation](recovery-and-reconciliation.md): prove the old Instance stopped or advance the generation and fence it before materializing the last durable checkpoint elsewhere.
