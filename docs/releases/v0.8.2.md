# SecondBox v0.8.2

SecondBox v0.8.2 adds tenant-aware egress contexts: several application installations share one RunnerPool while each keeps its own gateway endpoint, egress proxy, workload PKI, interception authority, policies, and credential custody. An operator gives a Tenant at most one nullable egress-context name; a Sandbox pins that name at creation; placement requires a Runner that advertises the pinned context; and every Runner backend compiles network policy from a strict context-indexed gateway mapping configuration. Routing is fixed by SecondBox authority and Runner assignment — Sandbox callers, Subjects, application authorities, guest headers, and guest source addresses cannot select or override it.

v0.8.0 and v0.8.1 were tagged but retracted before publication: no GitHub Release or coordinated artifacts were published for either. v0.8.0's Go module coordinate is unusable because its root module graph required an unpublished Runner submodule; v0.8.1 predates the release qualification-driver fixes. Use v0.8.2.

Every Profile network policy now states `requiresTenantEgressContext` explicitly. The Runner protocol advances to generation 4 exactly: control planes and Runners must be replaced together, and generation 3 peers, legacy global-gateway assignments, default contexts, and cross-context fallback are refused. The Runner's former global logical-gateway environment map is removed; Runners load `SECONDBOX_RUNNER_EGRESS_CONTEXT_CONFIG`, a strict read-only JSON file rendered by the deployment tooling. New platform-only surfaces: `PUT /v1/tenants/{tenantRef}/egress-context` (revision-fenced, idempotent) and `GET /v1/diagnostics/egress-contexts` with the matching `secondbox` CLI commands.

Firecracker remains the only supported production backend. The published Firecracker bundle and trust anchor are unchanged from v0.6.0.

## Clean-recreation boundary

v0.8.2 does not support an in-place update from v0.7.2 or any earlier release. `secondbox-deploy` refuses the update before mutating anything and prints the recreation procedure. There is no historical Profile decoder, legacy assignment bridge, or Sandbox migration operation.

To move a deployment to v0.8.2:

1. Quiesce every consuming application and stop every Sandbox.
2. Take one coordinated backup of the old PostgreSQL database, deployment state, Runner identity, and workspace filesystems. This backup is a rollback input only; it cannot be imported into v0.8.2.
3. Retire the old Sandboxes and remove the old deployment database, Runner state, and workspaces through the documented recreation procedure.
4. Initialize v0.8.2 as a clean install, apply its standard resources, and recreate Tenants, authorities, Profiles, and Sandboxes under the new contracts.

Roll back only by stopping the new deployment and restoring the complete coordinated backup. Never combine old global-gateway configuration with the new database or Runner state.

New installations use the ordinary guided or production path:

```sh
curl -fsSL https://github.com/SecondStack-AI/SecondBox/releases/download/v0.8.2/install.sh | sh
```

Install SDKs at the coordinated v0.8.2 version:

```sh
npm install @secondstack-ai/secondbox@0.8.2
go get github.com/SecondStack-AI/SecondBox@v0.8.2
```
