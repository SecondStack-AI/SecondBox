# SecondBox v0.31.0

## Deployment boundary

Deployments from v0.14.0 onward update in place and retain their Sandboxes,
Workspaces, Profiles, and authorities. There is no database migration. Public
API v1, Runner protocol generation 7, and standard Profile revisions are
unchanged, so v0.30.0 and v0.31.0 peers connect in either update order. The
amd64 Firecracker bundle and the gVisor materialization change; the arm64
Firecracker bundle does not.

Before updating, check two configurations that the control plane now refuses:

- `SECONDBOX_DATA_PLANE_MAXIMUM_SESSION_BYTES`
  (`overrides.data_plane_maximum_session_bytes`) must be unset or at least
  65,536. The control plane does not start, and `secondbox-deploy` does not
  resolve the manifest, with a smaller value.
- A Profile that declares ports needs `execution.streamWindowBytes` of at
  least 65,536. New revisions with a smaller window are refused. A Sandbox
  pinned to an older revision with a smaller window keeps its direct
  PortSessions, but its proxied PortSessions are refused. Publish a revision
  with a larger window, then switch each affected Sandbox to it with
  `:switch-profile` while it is stopped and Snapshot-free, or recreate it.

Neither configuration could carry a working proxied Port tunnel before.

Update the control plane and every Runner. Install the new amd64 bundle and
the new gVisor materialization on each Runner of that backend; existing
Sandboxes start on them at their next start. When upgrading from an earlier
release, also follow the [v0.30.0 notes](v0.30.0.md) and the intervening
release notes.

## Port tunnels

- **Guest frame order.** The guest agent assigned a Port frame's sequence
  before it took its send lock. When it returned write credit while forwarding
  guest output, a later frame could leave first, and the Runner failed the
  PortSession. It now holds the lock across both, as every other guest sender
  does. The fix ships in the guest agent, so a Sandbox receives it only from
  the new amd64 bundle, the new gVisor materialization, or a client-selected
  image rebuilt with this release's image builder.
- **Message bound.** One proxied `secondbox.port.v1` message carries at most
  65,536 bytes, the most Port credit a Runner grants. On a Profile with a larger
  window, a larger message used to wait for credit until the session expired;
  the control plane now closes the WebSocket with "message too big". The
  TypeScript `PortTunnel.send` and Go `PortTunnel.Write` split writes into
  messages within the bound and preserve byte order, not message boundaries,
  so callers no longer chunk. The bound is `PortTunnelMaximumMessageBytes` in
  Go and `PORT_TUNNEL_MAXIMUM_MESSAGE_BYTES` in TypeScript.
- **Failed writes.** A failed TypeScript `send` may leave part of its payload
  delivered, so it now rejects that send and every later one. Before, a later
  send continued the partly written stream.
- **Diagnostics.** A guest's normal close of its loopback socket is reported
  as a closed PortSession on both transports; it was reported as a failed
  read. A guest frame that breaks the stream contract is reported as
  "guest port protocol violation". The Runner logs the cause of failed Port
  opens, writes, and reads, which it used to discard.

## Bundle identity

The amd64 Firecracker bundle `secondbox-0.31.0` replaces `secondbox-0.17.0`.
It carries the guest agent of this release (built from `4d4891c`), the shipped 6.12.94 guest kernel,
and a guest root filesystem built from the 2026-10-26 Debian and Debian
security snapshots, so it also installs `ca-certificates`
`20250419~deb12u2`. Workloads in amd64 Firecracker Sandboxes on the default
image that use the system trust store no longer trust the compromised eMudhra
intermediates described in the [v0.29.0 notes](v0.29.0.md#emudhra-intermediate-ca-compromise)
once their Runner installs the bundle and the Sandbox restarts.

- Bundle `manifest.json`: `sha256:d7e570672f872781798f96f4026f1f068254ede3604bd0f9bc540111aab084cc`
- Runtime component `secondbox-0.31.0-runtime`: `sha256:2337d9c0556e7aea50dc7b16d6105b15e1151cbdef3a3141517d2aa06554231b`
- Toolchain component `secondbox-0.31.0-toolchain`: `sha256:4106e8add67196e10e0a588773e28c3f91384b198239cb6f2d844196f733a64e`

The arm64 bundle is unchanged from v0.30.0. Its guest agent keeps the Port
frame-order defect and its trust store keeps the compromised intermediates
until a later release replaces it. arm64 Sandboxes still receive the
control-plane and SDK changes above.

Take the bundle and gVisor materialization digests from the verified artifact
manifest for the selected architecture.

## Distribution

The default lean release qualifies Firecracker and local gVisor and publishes
Linux amd64 OCI images, and the arm64 artifact set publishes the
control-plane, Runner, installer-tools, and microVM-artifact images for Linux
arm64. CLI and deployment binaries ship for Linux and macOS on amd64 and
arm64. It includes the Btrfs-image installer qualification; it does not
include gVisor pod qualification.

Install the TypeScript SDK with `npm install @secondstack-ai/secondbox@0.31.0`.
The Go module is `github.com/SecondStack-AI/SecondBox@v0.31.0`.
