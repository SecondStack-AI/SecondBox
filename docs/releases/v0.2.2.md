# SecondBox v0.2.2

SecondBox v0.2.2 is a patch release that stops single poison records from taking down the whole control plane or locking a runner into a reconnect loop.

## The failure mode

A family of durable-authority assertions returned bare errors that the reconciler loops treat as fatal, or dropped the entire runner gRPC session over one bad message. Because the offending row was never mutated, the same record was re-picked after every restart: one poison record became a permanent, self-sustaining outage of every Sandbox in the deployment. The quarantine machinery — degrading contention to a deferred retry — already existed; these paths simply missed it.

## The fixes

Control-plane fatal paths are now quarantined. A terminal Assignment failure coinciding with an in-flight Workspace stop, an Assignment whose durable command payload cannot be validated, an invalid Profile revision, a delete effect recorded as succeeded without a finalized Sandbox, and a lost generation race all defer the affected row with backoff and a logged warning while the rest of the deployment keeps running.

Lifecycle stop commands no longer share `runner_commands` `kind='fence'` with the assignment reconciler, whose bulk fence expiry could collaterally expire a lifecycle-owned command and trip a fatal delivery guard; they now carry `kind='lifecycle_fence'`, and a schema migration retags the rows current stop effects reference. A stop that exhausts its retries also releases the Workspace stop mutation it holds — previously the slot leaked forever, blocking the restart that recovers a failed Sandbox.

Runner sessions are no longer dropped over replays. A result for an already-completed local-workspace effect is absorbed as a no-op even after the Workspace row has moved on, and `AssignmentProgress` stage timings are truncated to the microsecond precision PostgreSQL stores, so an exact replay of the same message no longer reads as different evidence. Genuine authority conflicts now name each divergent field, and telemetry disagreement is logged without affecting the control connection.

## Upgrading an affected deployment

The schema migration runs automatically before the control plane opens its listeners. Rows that previously killed the process are deferred and logged on the new version; watch for `WARN` entries naming deferred Assignments, invalid Profiles, or discarded telemetry to find records that need operator attention. Workspace stop mutations leaked by stop failures on earlier versions are not retroactively released: a Workspace stuck with `mutation_kind='stop'` whose stop effect is in `runner_failed` can have its mutation columns cleared manually once the deployment is upgraded.

## Install

Download `secondbox` and `secondbox-deploy` for your OS and architecture from the assets below. For Linux amd64:

```sh
mkdir -p ~/.local/bin
curl -fLO https://github.com/SecondStack-AI/SecondBox/releases/download/v0.2.2/secondbox_0.2.2_linux_amd64
curl -fLO https://github.com/SecondStack-AI/SecondBox/releases/download/v0.2.2/secondbox-deploy_0.2.2_linux_amd64
install -m 0755 secondbox_0.2.2_linux_amd64 ~/.local/bin/secondbox
install -m 0755 secondbox-deploy_0.2.2_linux_amd64 ~/.local/bin/secondbox-deploy
```

Install an SDK at the same version:

```sh
npm install @secondstack-ai/secondbox@0.2.2
go get github.com/SecondStack-AI/SecondBox@v0.2.2
```

## Runtime requirements

Executing Sandboxes requires a Linux amd64 Runner host with KVM and TUN, cgroup v2, and a dedicated XFS or Btrfs workspace filesystem with reflink support. The control plane can run separately; only the Runner needs access to these host facilities.
