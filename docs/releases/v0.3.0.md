# SecondBox v0.3.0

SecondBox v0.3.0 is a minor release that adds snapshot-resume Sandbox startup. A `snapshot_resume` Profile reaches `ready` in 125/130 ms p50/p95 on the unsaturated `start → ready` path, against 447/489 ms for the same deployment's cold boot.

It also carries two schema migrations, one breaking contract change for clients that create Profiles, a new required Runner manifest key, and a rebuilt microVM bundle under a new trust anchor. Read the upgrade path before deploying.

## Upgrade path

Upgrade from v0.2.3. There is no intermediate step, and no operator action is needed for the migrations themselves — but three of the items below do require operator action.

### 1. Two migrations run automatically at control-plane start

Migrations run before the control plane opens its listeners. Both are idempotent and neither re-executes prior work.

- `0014_lifecycle_quiescent_schedule` redefines `sandboxes_lifecycle_reconcile_idx` so it holds one entry per *scheduled* Sandbox rather than one per Sandbox, and parks the resting population an upgraded deployment already carries. Without that second half, every resting Sandbox would be claimed once on the first poll after upgrade. It deliberately does not touch `revision`, because parking changes nothing observable.
- `0015_profile_startup_mode` stamps every Profile revision that carries no `startup` key with `cold_boot`. Revisions written before the field ran exactly one startup path — they booted the guest — so this states the behavior they already had rather than inventing a default for them. The guard `WHERE NOT (spec_json ? 'startup')` keeps it idempotent and keeps it off a revision that already states a mode, so an upgraded database converges on exactly the `spec_json` a fresh one writes.

### 2. Breaking: `ProfileRevisionSpec` requires `startup.mode`

Every Profile revision must now state how its Instances reach `ready`. `startup` is a required object whose `mode` is explicitly `cold_boot` or `snapshot_resume`.

There is no application default. `validateProfileRevisionSpec` refuses a blank mode and the contract lists `startup` as required, so a client that creates or revises a Profile without one is refused. `StartupMode` is a named contract enum, so both SDKs emit typed constants rather than bare strings; regenerate against v0.3.0 and add an explicit mode at every call site that builds a Profile spec.

Existing Profile revisions are handled by migration `0015` and need no client change.

### 3. New required Runner manifest key

`snapshot_template_cache_root` is now a required key in every `[[runners]]` declaration, validated as an absolute Runner-host path and constrained to `/var/lib/secondbox-runner` for same-host Compose placement, exactly like `firecracker_jail_root`. It reaches the Runner as `SECONDBOX_RUNNER_SNAPSHOT_TEMPLATE_CACHE_ROOT`.

It is deliberately required rather than optional: the golden memory file is hard-linked into every jail, so the cache must share a filesystem with the jail root, and that is a decision an operator makes rather than one the code guesses. `secondbox-deploy runner-template` emits it, and the documented scaffold block is kept byte-identical to the command output by test.

### 4. New microVM bundle and new trust anchor

This release ships a rebuilt microVM bundle signed by a new release key, and operators must install the new bundle and pin its public key through the runner init flow described in [release operator setup](../operations/release-operator-setup.md) and the [microVM image pipeline](../operations/microvm-image-pipeline.md).

The rebuild was necessary because the guest agent, `/init`, and the microVM entrypoint all live inside the signed rootfs, and template mode plus the one-time assignment bind changed all three.

**What requires the new bundle:** snapshot-resume, in every form — template capture, resume start, and the `snapshot-resume` Runner capability. An older rootfs cannot boot in template mode at all: its entrypoint aborts on the missing per-Sandbox identity kernel arguments that a template deliberately does not carry.

**What works unchanged against an older, already-verified bundle:** everything else. Cold boot, guest protocol negotiation, the Exec, File, PTY, and Port data plane, runtime secrets, post-restore hardening, Workspaces, Snapshots, and generation fencing. The frozen `contracts/guest/v1` descriptor is byte-identical to v0.2.3, so no guest wire contract changed.

**What changes for every Profile regardless:** digest pinning. A Profile pins the runtime and toolchain component-manifest digests it was created against, the control plane resolves those digests through its signed asset catalog into the references the Assignment carries, and a Runner refuses — before creating any Workspace, TAP, or jail — any Assignment whose component digests differ from its own locally verified manifest. Installing a different bundle therefore re-pins every Profile to that bundle, and the release-owned standard bundles are regenerated against the digests this release ships. Plan the bundle install, the asset catalog update, and the standard-resource apply as one coordinated step rather than three independent ones.

### 5. Runner and control-plane versions

A v0.3.0 Runner requires a v0.3.0 control plane: Assignments now carry `ProfileRequirements.startup_mode` and a Runner refuses an Assignment that does not state one, before it creates any resource. The reverse degrades cleanly — a v0.3.0 control plane with an older Runner works, because the older Runner never reports snapshot-resume readiness and therefore never attracts a `snapshot_resume` Profile.

## Snapshot-resume startup

### What it does

A cold boot spends most of its time booting a guest. On the 2026-08-06 baseline, guest negotiation was 377/391 ms of an unsaturated `create → ready`, 71% of the total, and under a burst of 32 it inflated 5.9× while the host paged in rootfs at 1.29 GiB/s — every Instance reflink-clones the rootfs, each clone is a distinct inode, and distinct inodes share no page cache, so 32 concurrent boots fault the same bytes from disk 32 times.

Snapshot resume removes both terms. There is no boot, so guest negotiation collapses to a snapshot load; and every resume maps one shared golden memory file, so the resident set of the first resume is the page cache of every later resume.

### Measured

Every number below is the control plane's own `operation_total` for the Operation named, not a client stopwatch. Zero refusals, zero failures.

| Workload | `create → ready` p50/p95 | `start → ready` p50/p95 |
|---|---:|---:|
| Concurrency 1, 10 arrivals | 198/522 ms | **125/130 ms** |
| Concurrency 4, 12 arrivals | 376/952 ms | 170/213 ms |
| Cold-boot baseline, same deployment | 529/1,370 ms | 447/489 ms |

Unsaturated `start → ready` sits 70 ms inside the 200 ms ceiling at p95, and resume removes 72% of cold boot. Unsaturated `create → ready` is 198 ms p50 and lands just inside the ceiling; its 522 ms p95 is Workspace provisioning's tail rather than guest startup, and that is the next optimization rather than part of this work.

The boot-stage attribution is the negative that matters, because every other assertion would still pass if the Runner had quietly cold booted:

| Stage | Resume p50/p95 | Cold boot p50/p95 |
|---|---:|---:|
| `guest_negotiation` | **68.8/75.6 ms** | **377/391 ms** |
| `compute_launch` | 8.7/11.7 ms | 7/16 ms |
| `network_setup` | 11.8/13.4 ms | 13/15 ms |
| `artifact_verify` | 0.3/0.7 ms | 0/835 ms |

### How it is built

The template is identity-neutral. The same signed rootfs boots two ways, selected by kernel argument: a tenant Instance boots with its full assignment identity, and a template boots with `secondbox.template_mode=1` and none at all — no Sandbox ID, no Instance ID, no generation, no digests, no runtime secrets, an unmounted Workspace device, and a protocol listener that is bound but refuses every connection.

Identity arrives through one `POST /assignment/bind` request on the existing host-only vsock control endpoint, refused before post-restore hardening succeeds and refused for every request after the first. `contracts/guest/v1` is untouched.

The Workspace is mounted at bind rather than at boot. It is the one device whose backing file differs per Instance, and a template that mounted its sterile Workspace before capture would seal that superblock and page cache into every resumed Instance — which no drive override can correct, because Firecracker opens block devices during the load, at the paths the VM state recorded.

That same property is why **snapshot resume requires the jailer**. Only chroot-relative recorded paths let each Instance resolve its own disks inside its own jail, so staging — not an API call — is what delivers a per-Sandbox Workspace. An unjailed resume is refused before any file is staged, and `snapshot_resume` is incompatible with the Runner's test-only unjailed mode.

A resumed guest also cannot be given a network interface its template did not capture: only the host-side TAP is overridable and the guest MAC is not. So a template records the network device its Runner's configuration gives guests, captured link-down and address-less, and the guest installs its own hardware address, address, link state, and default route over rtnetlink as the last step of the bind — after the Workspace mount, so nothing can leave a guest whose identity is incomplete.

### Operator requirements

Snapshot resume is opt-in and currently requires deliberate operator setup. Four things must all hold before a Runner advertises the capability:

1. **Template cache root configured** — `snapshot_template_cache_root` in the Runner's manifest declaration, on the same filesystem as the jail root.
2. **The jailer required** — a Runner that allows unjailed operation cannot resume and never advertises the capability.
3. **A published template built from that Runner's exact bundle** — matched on artifact version, architecture, and the runtime and toolchain bundle digests.
4. **A `snapshot_resume` Profile aimed at a pool that declares the capability** — both shipped standard bundles are `cold_boot`, so resume requires an operator-authored Profile.

**Template generation is not yet a Runner operation.** Templates are built by the qualification harness, so in a production deployment no Runner advertises `snapshot-resume` until an operator publishes one, and the observable behavior of a `snapshot_resume` Profile is a typed refusal at admission. The interim flow is exercised rather than described: the scenario suite publishes a template into the Runner's cache, with the Runner's own environment, before the Runner starts. The cache's on-disk contract is one directory named by the template ID holding `manifest.json`, `vmstate.snap`, `memory.snap`, and `rootfs.ext4`, so a Runner-side generator will replace the caller rather than the contract.

There is **no silent cold boot**. A `snapshot_resume` Profile that cannot resume is refused with a typed error — non-retryable `startup_mode_unsupported` (409) for a pool that never declares resume capacity, and the existing retryable refusals for a declared pool with no advertising Runner or an unavailable template.

## Lifecycle latency and correctness

Teardown got attribution first and then a fix. Nine drain, stop, and delete milestones are now persisted by the transactions that establish them, which located the cost exactly: two transitions that determine their own successor were each waiting out a full recovery poll interval that no external work occupied. Committing those at their own clock moves client-visible `delete → deleted` p50 from 506 to 299 ms and `stop → stopped` from 339 to 229 ms, with create and start unchanged.

A no-op reconciliation no longer moves a Sandbox's ETag. A pass that decides to wait changes no field a caller can observe, and previously advanced `revision` and `updated_at` anyway — at a 100 ms interval that is about ten revisions per second of pure noise while a Runner is being waited on, each one able to turn a caller's `If-Match` into a spurious 412. Sandboxes at rest now park their schedule entirely, and start deferrals for an unresolvable Profile revision or an unavailable home Runner hold their revision while staying scheduled.

## Install

Download `secondbox` and `secondbox-deploy` for your OS and architecture from the assets below. For Linux amd64:

```sh
mkdir -p ~/.local/bin
curl -fLO https://github.com/SecondStack-AI/SecondBox/releases/download/v0.3.0/secondbox_0.3.0_linux_amd64
curl -fLO https://github.com/SecondStack-AI/SecondBox/releases/download/v0.3.0/secondbox-deploy_0.3.0_linux_amd64
install -m 0755 secondbox_0.3.0_linux_amd64 ~/.local/bin/secondbox
install -m 0755 secondbox-deploy_0.3.0_linux_amd64 ~/.local/bin/secondbox-deploy
```

Install an SDK at the same version:

```sh
npm install @secondstack-ai/secondbox@0.3.0
go get github.com/SecondStack-AI/SecondBox@v0.3.0
```

## Runtime requirements

Executing Sandboxes requires a Linux amd64 Runner host with KVM and TUN, cgroup v2, and a dedicated XFS or Btrfs workspace filesystem with reflink support. The control plane can run separately; only the Runner needs access to these host facilities.

Snapshot-resume additionally requires the jailer, a configured template cache root on the jail root's filesystem, and a published template matching the Runner's signed bundle.
