# SecondBox v0.5.0

SecondBox v0.5.0 removes the application Artifact resource and the control plane's S3-compatible object-store dependency. It also fixes long-running HTTP operations that could complete successfully on the server after the client connection had already been cut off.

This is a deliberate clean break for the pre-production contract. Read the upgrade path before using a v0.5.0 control plane, SDK, or deployment manifest.

## Upgrade path

There is no supported in-place upgrade from v0.4.7 or earlier. SecondBox has no production deployments to preserve, so v0.5.0 removes the old schema and configuration instead of carrying a migration or compatibility layer.

- Recreate PostgreSQL from the v0.5.0 baseline and render a fresh `secondbox.toml`. Do not point v0.5.0 at an older database or pass an older deployment manifest and expect it to be upgraded.
- Treat existing development Sandboxes and their Runner-local Workspaces as disposable. The new deployment does not import old Sandbox records, Workspace ownership, or application Artifact data.
- Upgrade clients with the server. Artifact endpoints, generated types, high-level SDK methods, and CLI commands no longer exist. `RetentionPolicy` no longer carries `artifactRetentionSeconds`, and subject quota policy no longer carries Artifact count or byte limits.
- Remove the `[object_store]` manifest section, object-store images, S3 credentials, bucket configuration, and object-store tuning overrides. Guided installation and Compose now deploy PostgreSQL, the control plane, and the Firecracker Runner without an object store.
- Apply selected release-owned standard bundles to the fresh deployment. Their immutable Profile documents are generated against the v0.5.0 contract, whose `RetentionPolicy` no longer carries Artifact retention. They are not an append-only continuation of a v0.4.7 Profile lineage, while their compute, lifecycle, execution, and network behavior is otherwise unchanged.

The Runner protocol, guest protocol, guest agent, `/init`, microVM entrypoint, and Firecracker backend are unchanged. The existing microVM bundle and trust anchor carry forward, so no bundle rotation is required. The public HTTP contract and deployment contract do change, and the database baseline is intentionally incompatible.

## Application Artifacts and S3 removed

The removed Artifact resource was a bounded immutable upload/download surface backed by S3-compatible storage. v0.5.0 removes it end to end:

- `/v1/sandboxes/{sandboxId}/artifacts` and `/v1/artifacts/*`;
- Artifact request, response, pagination, SDK, and CLI surfaces;
- Artifact count and byte quotas plus retention and garbage collection;
- Artifact PostgreSQL tables, object-store metadata, and S3 client code;
- object-store deployment configuration, bundled Compose services, credentials, ports, health checks, and backup handling.

Applications that need to place an external file in a Sandbox should use the existing bounded File API or SDK `writeFile` operation against that Sandbox's generation and Lease. Those bytes become ordinary Workspace data and follow the Sandbox's runner-local durability rules; they are not an immutable cross-Sandbox object resource.

The release `artifact manifest` remains. It is the verified description of immutable execution and distribution assets published through the GitHub Release and GHCR, including the signed microVM manifest identity; it is not the removed application Artifact API and not a control-plane S3 dependency.

## Long-running HTTP responses stay connected

The public server's connection timeout previously became `net/http.Server.WriteTimeout` for the entire handler lifetime. A Buffered Exec or another valid operation that ran longer than 30 seconds could finish and persist its result, then fail when the handler finally tried to write the response. Go callers received `EOF`; TypeScript callers received `fetch failed`.

Ordinary responses now start their write deadline only when response output begins. Handler work remains bounded by the operation or Profile deadline, while a client that stops reading is still bounded once the server starts emitting bytes. Exec, Terminal, and Port upgrades retain their session-specific write deadlines.

The Go and TypeScript Sandbox wait helpers now use request windows up to the public 60-second service bound while still respecting the caller's remaining deadline. Production reverse proxies and load balancers must allow the longest admitted Profile operation, 60-second waits plus transport overhead, and the full lifetime of upgraded sessions.

## Install

Create a fresh guided single-host deployment with:

```sh
curl -fsSL https://github.com/SecondStack-AI/SecondBox/releases/latest/download/install.sh | sh
```

Install SDKs at the same coordinated version:

```sh
npm install @secondstack-ai/secondbox@0.5.0
go get github.com/SecondStack-AI/SecondBox@v0.5.0
```
