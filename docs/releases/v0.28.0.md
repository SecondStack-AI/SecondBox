# SecondBox v0.28.0

## Deployment boundary

Deployments from v0.14.0 onward update in place and retain their Sandboxes,
Workspaces, Profiles, and authorities. The Runner protocol stays at generation
7, and the Firecracker bundles, gVisor materialization inputs, and standard
Profile revisions are unchanged. Every change is in the control plane, so the
Runners need no update, and v0.27.1 Runners connect to a v0.28.0 control plane.
Public API v1 gains two read operations and an optional
`capacityWaitMilliseconds` member on start and create.

Back up PostgreSQL before updating. Migration
`0038_start_capacity_wait_deadline` adds the nullable
`operations.capacity_wait_deadline` column without rewriting rows, and rollback
to v0.27.1 requires the backup. Stop every v0.27.x control-plane process before
v0.28.0 starts: an older lifecycle worker does not read the deadline, so it can
place a start that a v0.28.0 worker would expire.

When upgrading from an earlier release, also follow the
[v0.27.1 notes](v0.27.1.md) and the intervening release notes.

## Bounded start waits

Start admission returns a `pending` Operation and leaves placement to the
lifecycle worker. When the home Runner is full or unavailable, that start was
deferred indefinitely: it held the Workspace mutation slot, so stop and delete
were refused with `409 workspace_mutation_conflict`, and it booted compute
whenever the Runner freed up, whether or not its caller still waited.

- `POST /v1/sandboxes/{sandboxId}:start` accepts an optional
  `capacityWaitMilliseconds` from 1 to 3600000. A start not placed within it
  fails its Operation with the new retryable `capacity_wait_expired` problem.
  The same transaction releases the Workspace mutation slot, sets the desired
  state to `stopped`, and returns the start's compute quota reservation. The
  observed state, Workspace, and generation are unchanged.
- The bound is admission, not cancellation. A caller that gives up first still
  leaves the start pending until it places or expires. Expiry normally lands
  within one reconciliation poll interval after the deadline. A start that has
  already placed is never expired, and placement rechecks the deadline under
  the Sandbox lock, so a worker that lost its claim cannot place an expired
  start.
- The bound is part of the canonical request: reusing an `Idempotency-Key`
  with a different bound returns `409 idempotency_conflict`. An expired
  Operation stays failed, so a new start needs a fresh read of the Sandbox
  revision and a new key.
- `POST /v1/sandboxes` accepts the same member for the start that a Profile
  with a `running` initial state performs after creation, measured from create
  admission. On expiry the create Operation fails and the Sandbox remains,
  stopped, with its Workspace; start that Sandbox instead of creating another.
  A Profile with a `stopped` initial state ignores the bound.
- A start that omits the member waits as before.

The Go `StartSandboxRequest` and `CreateSandboxRequest` and the TypeScript
`start` and `createSandbox` options carry the member.

## Retry hints on compute quota

A `429 quota_exceeded` on which every exhausted dimension is a compute
dimension is now `retryable` and carries `retryAfterMilliseconds: 1000` with
`Retry-After: 1`, as `503 home_runner_unavailable` already did. The compute
dimensions are `maxActiveInstances`, `maxVcpuCount`, `maxMemoryBytes`, and
`maxConcurrentOperations` at Subject or Tenant scope, and a Profile's
per-Sandbox execution concurrency. The hint paces a retry; it does not promise
that the retry succeeds, and clients should add jitter.

These refusals keep the earlier non-retryable form without a hint:

- a refusal on `maxSandboxes`, `maxSnapshots`, or `maxPortSessions`, even when
  a compute dimension is exhausted too;
- a request that exceeds a compute limit on its own, such as a start under
  `maxActiveInstances: 0` or a Profile larger than the vCPU or memory limit,
  because no work ending frees it.

`409 execution_node_unavailable` carries no hint.

## RunnerPool capacity

`GET /v1/pool-capacity` (application authority with `sandbox:read`, or the
platform token) and `GET /v1/tenant-pool-capacity` (tenant controller) return
one entry per RunnerPool the caller can place into or already has Sandboxes in.
Each entry reports the pool state, `placeableRunnerCount`, the allocatable and
reserved Instances, vCPU, memory, and concurrent-operation slots of those
Runners, `pendingStartCount`, and `storageAdmissionDeniedRunnerCount`.

The figures aggregate every Tenant placing into the pool and name no Runner,
Tenant, or Sandbox, though a pool with one placeable Runner reports that
Runner's figures. A Sandbox is homed on one Runner, so free pool capacity does
not mean that its home has room, and the reading is not a reservation. The Go
and TypeScript SDKs add `GetPoolCapacity`/`getPoolCapacity` and
`GetTenantPoolCapacity`/`getTenantPoolCapacity`; there is no CLI verb. See
[Observability and diagnostics](../operations/observability-and-diagnostics.md#runnerpool-capacity).

## Distribution

The default lean release qualifies Firecracker and local gVisor and publishes
Linux amd64 OCI images, and the arm64 artifact set publishes the
control-plane, Runner, installer-tools, and microVM-artifact images for Linux
arm64. CLI and deployment binaries ship for Linux and macOS on amd64 and
arm64. It includes the Btrfs-image installer qualification; it does not
include gVisor pod qualification.

Install the TypeScript SDK with `npm install @secondstack-ai/secondbox@0.28.0`.
The Go module is `github.com/SecondStack-AI/SecondBox@v0.28.0`.
