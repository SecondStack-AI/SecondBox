# SecondBox v0.9.2

SecondBox v0.9.2 repairs workspace file reads through the data plane. On any deployment whose Profile `maximumTransferBytes` is larger than the control plane's `SECONDBOX_DATA_PLANE_MAXIMUM_SESSION_BYTES`, every read of every file was refused with `413 limit_exceeded` before the Runner was contacted, no matter how small the file was. Each release-owned Profile declares a transfer limit above the default session cap, so the defect reached ordinary installations, and writes to the same paths continued to succeed. Reads without a caller-supplied bound are now admitted against the smaller of the two ceilings.

The release also gives three refusals their own types. A requested output limit or stream window above the pinned Profile now answers `400 invalid_request` naming the exceeded bound, and a payload above `maximumTransferBytes` answers `413 limit_exceeded`. All three previously answered `429 quota_exceeded`, which callers could not distinguish from a concurrency refusal, and the bound was only checked after capacity, so a malformed request against a saturated Sandbox was reported as a quota refusal. A file that genuinely exceeds the admitted bound now returns `413 limit_exceeded` from the Firecracker and gVisor backends instead of a `500`.

This patch does not change the public API, database schema, Runner protocol, guest protocol, standard resource specifications, or the signed Firecracker microVM bundle. The published bundle and trust anchor are unchanged from v0.6.0, so no Profile is repinned and no coordinated bundle install is required. Firecracker remains the supported production backend, with gVisor supported for Linux amd64 hosts without KVM.

## Upgrade

Guided Firecracker installations at v0.8.3 or newer upgrade in place with the v0.9.2 bootstrap. Take and verify a PostgreSQL backup, stop every Sandbox, and run the preflight before the mutating update:

```sh
curl -fsSL https://github.com/SecondStack-AI/SecondBox/releases/download/v0.9.2/install.sh \
  | sh -s -- update --check /absolute/path/to/secondbox-install-operation
curl -fsSL https://github.com/SecondStack-AI/SecondBox/releases/download/v0.9.2/install.sh \
  | sh -s -- update /absolute/path/to/secondbox-install-operation
```

Deployments at v0.6.0 through v0.7.2 cannot update in place. The installer refuses them at the v0.7.2 tenant-egress clean-recreation boundary and prints the recreation procedure it requires: quiesce consuming applications, retire every pre-v0.8.0 Sandbox, take and verify a coordinated PostgreSQL, deployment-state, Runner-identity, and Workspace backup for rollback only, stop and purge the old deployment through its recorded uninstall procedure, then initialize v0.9.2 and recreate Tenants, authorities, Profiles, Runner context mappings, and Sandboxes. Pre-v0.8.0 state is never combined with a generation-4 deployment.

gVisor deployments composed by Kubernetes operators replace the control-plane and Runner images with the v0.9.2 digests recorded in the artifact manifest. The gVisor materialization identities move with the release images as usual.

Operators who lowered a Profile's `maximumTransferBytes` to the session cap to work around the read failure can raise it again. The admitted bound for a read is the smaller of that limit and the session cap, so the cap alone governs how large a single read may be.

Install SDKs at the coordinated v0.9.2 version:

```sh
npm install @secondstack-ai/secondbox@0.9.2
go get github.com/SecondStack-AI/SecondBox@v0.9.2
```
