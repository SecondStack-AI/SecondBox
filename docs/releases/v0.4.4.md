# SecondBox v0.4.4

SecondBox v0.4.4 supersedes the unpublished v0.4.0 through v0.4.3 tags. It contains the guided single-host installer and CLI presentation release described in the [v0.4.0 notes](v0.4.0.md), the qualification fixes described in the [v0.4.1](v0.4.1.md), [v0.4.2](v0.4.2.md), and [v0.4.3](v0.4.3.md) notes, and a firewall-independent network transport for the disposable installer qualification guests.

## Fixed

- Installer qualification assigns each guest a deterministic MAC address, includes a matching NoCloud v2 configuration that requires IPv4 DHCP, and connects it through QEMU's isolated user network. A verified localhost-only SSH forward gives the driver access without depending on host firewall rules for libvirt bridge DHCP or DNS.
- A guest that remains unreachable now emits the final 120 lines of its dedicated serial console before the driver removes the domain and disk images.
- A new filesystem-image installation now revalidates backing capacity through the nearest existing safe ancestor. Its operation-specific image parent does not exist until privileged apply, so checking that exact directory previously rejected every first installation before creating host resources.
- The installer-tools image now invokes the Debian `btrfs-progs` formatter at `/usr/sbin/mkfs.btrfs`. Its former `/usr/bin` entrypoint was not present in the image and prevented every filesystem-image installation from formatting its fully allocated backing file.
- Root-owned host resources are now revalidated through the private sudo helper on resume, including the recorded Workspace device identity. Unprivileged postcondition validation verifies their exact plan-and-receipt identity without traversing the intentionally root-only Runner directory, which previously ended every install after host apply with `permission denied`.
- MicroVM artifact extraction now supplies an inert create-time entrypoint before copying files from the release-pinned OCI image. The artifact-only image intentionally has no configured command, so bare `docker create` previously rejected every installation during release asset materialization.
- Release materialization now preserves safe invoking-user directory parents that predate the installation, including a private `~/.local`. The previous exact create-time mode check rejected a normal pre-existing `0700` parent even though it was owner-controlled and the installer neither created nor claimed it.
- Completed host apply now records the Workspace filesystem's stable Btrfs or XFS UUID instead of its transient Linux device number. Filesystem-image installs therefore resume after reboot even when systemd assigns the image a different loop device, while resume and purge still reject a different filesystem at the reviewed path.
- The privileged runtime qualification allocates an explicit isolated Compose backend subnet instead of depending on Docker's finite default address pools, so a host with many unrelated Docker networks can still qualify without deleting them.
- Installer-owned Runner enrollment, Compose lifecycle, and diagnostics now consume the private host helper's accepted root-path verification instead of repeating same-host preflight as the unprivileged operator. Root-only Runner state remains inaccessible to the invoking user without blocking installation after deployment materialization.
- Installer readiness now accepts the public `pre_shared` credential state emitted for a ready, authenticated Runner instead of waiting for the nonexistent `active` projection until its five-minute deadline expired.
- Single-host capacity planning now reserves the 16 concurrent operations required by each `durable-coding` Sandbox. Readiness verifies that exact capacity, Runner pool, and scheduling capability set before the smoke Sandbox, instead of accepting an incompatible Runner and failing creation with `home_runner_unavailable`.
- Installer qualification now attributes every driver and guest-shell failure to its mode and source line, and includes the bounded guest serial tail for driver-side failures instead of silently cleaning the only diagnostic state.

The deployment change is limited to generated single-host Runner capacity and readiness checks; no database, public API, Runner protocol, guest, Profile, or microVM-bundle change is involved. Existing v0.3.1 deployments follow the compatibility and upgrade guidance in the v0.4.0 notes.

## Download and install

```sh
curl -fsSL https://github.com/SecondStack-AI/SecondBox/releases/latest/download/install.sh | sh
```

Standalone binaries and SDKs use version `0.4.4` and tag `v0.4.4`.
