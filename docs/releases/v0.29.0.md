# SecondBox v0.29.0

## Deployment boundary

Deployments from v0.14.0 onward update in place and retain their Sandboxes,
Workspaces, Profiles, and authorities. There is no database migration. Public
API v1, Runner protocol generation 7, the Firecracker bundles, and standard
Profile revisions are unchanged, so v0.28.0 and v0.29.0 peers connect in either
update order. The gVisor materialization changes.

Update the control plane, every Runner, every image fetcher, and the
`secondbox` and `secondbox-deploy` binaries. Every binary of v0.28.0 and
earlier was built with Go 1.25.12, which does not distrust the compromised
certificate authorities described below. Rebuilding or restarting an old
image does not pick up the fix; deploy the v0.29.0 images.

When upgrading from an earlier release, also follow the
[v0.28.0 notes](v0.28.0.md) and the intervening release notes.

## eMudhra intermediate CA compromise

The private keys of eight eMudhra intermediate certificate authorities are
recoverable, so anyone can issue a certificate for any domain that chains to a
publicly trusted root. A TLS client is protected only if its verifier or its
trust store distrusts those intermediates.

- SecondBox builds with Go 1.26.10. Its `crypto/x509` rejects chains through
  the compromised intermediates whatever trust store it is given. Go 1.25 is
  out of support and receives no fix: a Go 1.25.12 binary given a trust store
  older than Debian `ca-certificates` `20250419~deb12u2` accepted a forged
  certificate. This covers the control plane, the Runner, the image fetcher,
  the gVisor guest agent, and the `secondbox` and `secondbox-deploy` binaries
  on every platform. The Firecracker guest agent ships inside the unchanged
  bundle and is not rebuilt.
- The control-plane, Runner, and gVisor Runner images are built from
  `debian:12.15-slim` and install `ca-certificates` `20250419~deb12u2`; the
  installer-tools image moves to the same base. The image fetcher pulls registry images through the
  image's `skopeo`, which relies on that trust store alone. Do not mount an
  older CA bundle over `/etc/ssl/certs` in Runner or image-fetcher containers.
- The gVisor flat root moves from Alpine 3.22.5 to 3.22.7, whose
  `ca-certificates-bundle` `20261020-r0` no longer trusts the compromised
  intermediates. Workloads in gVisor Sandboxes on the default image that use
  the system trust store are protected once their Runner installs the new
  materialization. A client-selected execution image keeps its own root
  filesystem and CA bundle on either backend, and a start that omits the image
  reuses the Sandbox's pinned digest. Rebuild the image with a current trust
  store, publish it, and select the new image explicitly on the next start of
  each affected Sandbox.
- The Microsandbox probe and helper lock `rustls-webpki` 0.103.16 and
  `webpki-roots` and `webpki-root-certs` 1.0.11.

The Firecracker guest root filesystem in the `secondbox-0.17.0` and arm64
bundles is unchanged. It is built from a 2025-07-01 Debian snapshot with
`ca-certificates` `20230311`, which still trusts the compromised intermediates,
so workloads in Firecracker Sandboxes on the default image that use the system
trust store remain exposed until a later release ships a replacement bundle.
The guest root filesystem is discarded when an Instance stops, so installing a
newer `ca-certificates` in a running guest lasts only until then. A workload
that cannot wait can keep a current CA bundle in its Workspace and point its
TLS client at it alone. Go and OpenSSL clients also read the guest's
certificate directory, so set `SSL_CERT_FILE` to the bundle and `SSL_CERT_DIR`
to an empty Workspace directory.

The committed guest image definitions now pin dated Debian and Debian security
snapshots, and the rootfs build applies the security updates, so a bundle
built from them carries `ca-certificates` `20250419~deb12u2`. This release
does not ship such a bundle.

## Loopback API in production

Production accepts `tls_termination = 'loopback'` for an installation whose
API clients run on the control-plane host. `public_base_url` must be exactly
`http://127.0.0.1:<api_published_port>` and `api_bind_ip` must be `127.0.0.1`;
no TLS terminator or DNS name is needed. Remote Runners keep their mTLS
listener, and every other production requirement is unchanged. Returned Exec,
terminal and proxied Port tunnel URLs are `ws://127.0.0.1:...`, so a client in
a container must rebase them onto its own route to the API. See
[Loopback API in production](../operations/deployment.md#loopback-api-in-production).

## gVisor materialization

The `gvisor-artifacts` image carries the new flat root and a guest agent built
with Go 1.26.10, so its materialization digest changes. Take
`SECONDBOX_GVISOR_MATERIALIZATION_DIGEST` from the verified artifact manifest
and replace the assets while each gVisor Runner is stopped. Placement and
default-image starts use whichever materialization the home Runner has
verified, so existing Sandboxes start on the new flat root.

## Release hosts

Release runners need Go 1.26.10 as `RELEASE_GOROOT`; the release scripts
refuse a toolchain that differs from `go.mod`. A `golangci-lint` on the runner
path must be built with Go 1.26 or later. CI and the release workflows use
Node.js 24.22.1.

## Distribution

The default lean release qualifies Firecracker and local gVisor and publishes
Linux amd64 OCI images, and the arm64 artifact set publishes the
control-plane, Runner, installer-tools, and microVM-artifact images for Linux
arm64. CLI and deployment binaries ship for Linux and macOS on amd64 and
arm64. It includes the Btrfs-image installer qualification; it does not
include gVisor pod qualification.

Install the TypeScript SDK with `npm install @secondstack-ai/secondbox@0.29.0`.
The Go module is `github.com/SecondStack-AI/SecondBox@v0.29.0`.
