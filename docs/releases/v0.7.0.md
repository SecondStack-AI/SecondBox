# SecondBox v0.7.0

SecondBox v0.7.0 makes the Runner compute boundary concrete across three implementations. Firecracker remains the only supported production backend. Experimental Microsandbox runners exercise the same durable Sandbox lifecycle on Linux KVM and Apple Silicon macOS, while an experimental gVisor runner serves Linux amd64 hosts without KVM.

This release also changes CPU resources and quotas from fractional milli-CPU values to whole vCPUs, removes the public process-limit promise, makes execution-asset identity provider-neutral, and advances the Runner protocol to generation 3. Read the coordinated upgrade procedure before activating v0.7.0.

## Upgrade from v0.6.0

Take and verify a PostgreSQL backup first. Migration `0019_vcpu_quotas_and_backend_kind` is forward-only; rollback after activation requires restoring the v0.6.0 database backup and redeploying v0.6.0 binaries.

For a completed guided v0.6.0 installation, stop every Sandbox and run the v0.7.0 bootstrap with `update --check` before the mutating update:

```sh
curl -fsSL https://github.com/SecondStack-AI/SecondBox/releases/download/v0.7.0/install.sh \
  | sh -s -- update --check /absolute/path/to/secondbox-install-operation
curl -fsSL https://github.com/SecondStack-AI/SecondBox/releases/download/v0.7.0/install.sh \
  | sh -s -- update /absolute/path/to/secondbox-install-operation
```

The guided updater stops and restarts its single Runner in the required order. For an operator-managed multi-runner deployment, stop every Runner, upgrade and start the control plane so it applies migration `0019`, then deploy and start only generation-3 Runners. Generation-1 and generation-2 Runners are refused, and a mixed-generation fleet is unsupported.

Update operator-owned inputs before activation:

- Replace Profile `cpuMillis` with whole-number `vcpuCount`, subject and tenant `maxCpuMillis` with `maxVcpuCount`, and guided-deployment `max_cpu_millis` and `default_subject_max_cpu_millis` with `max_vcpu_count` and `default_subject_max_vcpu_count`.
- Replace RunnerPool `capacityPolicy.maxCpuMillis` with `capacityPolicy.maxVcpuCount` before reapplying operator-authored RunnerPool resources.
- Remove Profile `processLimit`. Guest process counts are not host PID counts; the Firecracker backend now owns its host-side VMM and jailer PID ceiling.
- Remove `signatureKeyId` from manually authored asset catalogs. Firecracker trust remains explicit backend configuration, while shared asset identity contains only provider-neutral immutable digests and requirements.
- Set `SECONDBOX_COMPUTE_BACKEND=firecracker` in every directly managed Firecracker Runner environment, or regenerate Runner handoffs before starting the upgraded Runners.
- Review converted quotas after migration. Each stored milli-unit value rounds up independently to the whole vCPU that covered it, zero quotas remain zero, and only Profile resources floor at one vCPU. Existing work keeps running, but rounding can leave a Subject temporarily unable to start more work until usage falls or its quota is widened.

The supported Firecracker release path carries forward the v0.6.0 signed microVM runtime and toolchain bundles and their trust anchor unchanged. The v1 guided updater rejects an execution-bundle digest change because existing Sandboxes remain pinned to immutable Profile revisions. The guest protocol schema is unchanged.

## Experimental compute backends

Every Runner selects exactly one backend at startup. The first healthy Runner seals its RunnerPool to that private backend kind for the pool's lifetime; there is no per-Sandbox backend selection, pool mutation, or automatic fallback. Users continue to select an operator-created Profile bound to a named RunnerPool, and backend identity does not enter public resources.

The Microsandbox backend supplies the complete provider-neutral Exec, File, PTY, and Port data plane plus durable reflink Workspaces, Workspace Snapshots, generation fencing, and fail-closed network policy. Its qualified experimental paths are Linux with KVM and macOS arm64 with Hypervisor.framework. It supports `cold_boot` only, has no supported Linux deployment path, and requires operator-built, digest-pinned materialization inputs. See [experimental Microsandbox on macOS](../operations/microsandbox-macos.md).

The gVisor backend runs on Linux amd64 without KVM or TUN/TAP by using the `runsc` systrap platform. It enforces per-Sandbox cgroup v2 CPU and memory bounds, dedicated mount and network namespaces, nftables policy, loop-backed reflink Workspaces, generation fencing, and the complete provider-neutral data plane. It also supports `cold_boot` only and requires an operator-managed privileged Runner plus locally assembled and pinned `runsc`, guest-agent, and rootfs inputs. See [experimental gVisor runtime](../operations/gvisor-runtime.md).

Neither experimental backend is built or distributed by the release pipeline. The published Runner and microVM artifacts remain the qualified Firecracker distribution.

## Install and SDKs

Create a new guided Firecracker deployment with:

```sh
curl -fsSL https://github.com/SecondStack-AI/SecondBox/releases/latest/download/install.sh | sh
```

Install SDKs at the same coordinated version:

```sh
npm install @secondstack-ai/secondbox@0.7.0
go get github.com/SecondStack-AI/SecondBox@v0.7.0
```
