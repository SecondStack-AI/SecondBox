# SecondBox v0.24.0

## Deployment boundary

Deployments from v0.14.0 onward update in place and retain their Sandboxes,
Workspaces, Profiles, and authorities. Public API v1 gains the Profile switch
operation and changes the Subject Sandbox policy body (see below). The Runner
protocol window stays `[6,6]`, so v0.23.0 and v0.24.0 peers can connect in
either update order. The Profile switch and Subject policy changes are
control-plane only; update Runners as well to receive the direct File transport
fix below. The signed execution bundle,
trust anchor, and standard Profile revisions are unchanged from v0.23.0.

Back up PostgreSQL before updating the control plane. Migration
`0037_subject_sandbox_policy_profiles` rewrites stored Subject Sandbox policies,
so rollback to v0.23.0 requires the pre-update backup. Control planes before
and after the migration do not share Subject Sandbox policies: a v0.23.0 control
plane ignores a rewritten policy and resolves Profile defaults, and a policy it
writes with `profile` is ignored by v0.24.0. Update in this order:

1. Pause Subject Sandbox policy writes, for example from ControlTower.
2. Stop every v0.23.0 control-plane process, then start v0.24.0, which applies
   the migration. Runners can be updated before or after.
3. Deploy policy clients that send `profiles` and parse `desired.profiles`,
   then resume policy writes. After the update, a `PUT` body with `profile` is
   refused with `400 invalid_request`. When upgrading
from an earlier release, also follow the [v0.23.0 notes](v0.23.0.md) and the
intervening release notes.

## Profile switch

`POST /v1/sandboxes/{sandboxId}:switch-profile` repins a stopped Sandbox to
another Profile's current revision. The body is `{"profile": "<name>"}`; the
operation requires `sandbox:lifecycle`, `If-Match`, and `Idempotency-Key`, and
returns `200` with the Sandbox
([#208](https://github.com/SecondStack-AI/SecondBox/pull/208)).

- The Sandbox keeps its ID, Workspace, home Runner, generation, resources, and
  egress-context pin. Its next start builds the Assignment, including network
  policy and attributed-execution permission, from the new revision. An
  application can, for example, move a conversation's Workspace between an
  online and an offline network policy without losing its files.
- The Sandbox must be stopped with no Instance and no retained Snapshot, and
  its Workspace ready at the current generation. The target must be enabled,
  share the pinned RunnerPool, architecture, startup mode, and
  `network.requiresTenantEgressContext`, admit the pinned resources without
  re-rounding them, and the home Runner must advertise the capabilities its
  Assignments need.
- An application authority needs grants for both Profiles; a missing one
  returns `403 authorization_failed`. New refusal codes are
  `409 profile_incompatible`, with a `{field, reason}` detail naming `pool`,
  `architecture`, `startup.mode`, `network.requiresTenantEgressContext`,
  `resources`, or `homeRunner`, and `409 profile_switch_snapshots_present`.
- Lifecycle re-resolves against the target as creation would. A Sandbox already
  pinned to the target's current revision is returned unchanged, so a caller
  that lost the response converges by repeating it. A changed pin writes one
  `sandbox.profile.switched` audit event.
- The Go SDK adds `SandboxHandle.SwitchProfile`, the TypeScript SDK
  `switchProfile`, and the CLI `secondbox sandboxes switch-profile`.

## Subject Sandbox policy names a set of Profiles

`PUT /v1/subjects/{subjectRef}/sandbox-policy` takes `profiles`, 1 to 32 unique
Profile names, instead of `profile`:

```json
{
  "profiles": ["agent-workspace", "agent-workspace-offline"],
  "lifecycle": {"idleSeconds": 900, "maximumDurationSeconds": null},
  "attributedExecution": {"maximumConnections": 256}
}
```

- One lifecycle and attributed-connection selection applies to every named
  Profile at Sandbox creation, at each attributed Assignment, and when a
  Profile switch re-resolves lifecycle. A Sandbox switched between two named
  Profiles keeps the same limits, each still bounded by its own Profile's
  ceilings.
- Every named Profile must be granted to the Tenant
  (`403 grant_escalation_denied`), enabled, and admit the selection. A non-null
  `attributedExecution` requires attributed permission on every named Profile.
- An unchanged block may still be preserved above a tightened ceiling, but only
  for a Profile the stored policy already named.
- The `PUT` response observes the first named Profile; `GET ?profile=` observes
  any Profile. The observation's `desired` carries `profiles`.
- Migration `0037` rewrites each stored policy as a one-element set with the
  same values and Subject revision.

## Fixes

- Exec, file, Terminal, and Port admission check an application authority's
  Profile grant against the Sandbox's Profile as read under the admission lock,
  so a concurrent Profile switch cannot admit work under a stale grant.
  An idempotent replay of such a request requires grants for both the Profile
  its session was admitted under and the Sandbox's current Profile, so it
  cannot disclose a session another authority of the subject admitted under a
  Profile the caller lacks.
- A File read over the direct data-plane transport no longer intermittently
  fails with `500 internal_error` after the Runner delivered the complete
  result ([#203](https://github.com/SecondStack-AI/SecondBox/issues/203)).
  The Runner half of this fix keeps a direct connection readable after the
  terminal, so it takes effect once the Runners are updated.
  A failed direct data-plane write reports the retryable
  `execution_node_unavailable`, as on the proxied transport.

## Release tooling

A release can publish an arm64 artifact set beside the amd64 one under the same
tag, staged by `just release-arm64 VERSION AMD64_RELEASE_DIR` on a Linux arm64
KVM host. `releasecontract.ArtifactManifestLocation` and
`QualificationEvidenceLocation` take the guest architecture. A release without
an arm64 set publishes amd64 alone.

## Firecracker bundle and trust anchor

The release retains the signed `secondbox-0.17.0` Firecracker bundle and the
v0.12.0 RSA trust anchor. The public key's canonical DER SHA-256 remains:

```text
59c127f459b8c93ca422f2f6c5bd43ff1e17d50309a262b7aff1b07bf59a5ced
```

Standard Profile revisions and their spec digests remain unchanged from
v0.19.0. Use the released artifact manifest for exact bundle, image, and Profile
identities.

## Distribution

The default lean release qualifies Firecracker and local gVisor and publishes
Linux amd64 OCI images. CLI and deployment binaries ship for Linux and macOS
on amd64 and arm64. It includes the Btrfs-image installer qualification; it
does not include gVisor pod qualification or an arm64 control-plane image.

Install the TypeScript SDK with `npm install @secondstack-ai/secondbox@0.24.0`.
The Go module is `github.com/SecondStack-AI/SecondBox@v0.24.0`.
