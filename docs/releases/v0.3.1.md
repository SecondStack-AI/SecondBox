# SecondBox v0.3.1

SecondBox v0.3.1 is a patch release. It repairs the idle accounting that made a restarted Sandbox unusable, and it lets a deployment manifest name its Compose project so a second deployment on one host cannot seize the first.

## Upgrade path

Upgrade from v0.3.0. No operator action is required.

There is no migration in this release, no contract change, and no change to the guest agent, `/init`, or the microVM entrypoint. The v0.3.0 microVM bundle and its trust anchor carry forward unchanged, so no Profile is re-pinned and an already-installed bundle keeps working. If you are coming from v0.2.3 or earlier, read the [v0.3.0 release notes](v0.3.0.md) first — that release carries two migrations, a breaking contract change, a new required Runner manifest key, and a rotated trust anchor.

## Restarted Sandboxes were drained immediately

A Sandbox that idle-retired and was then restarted was drained again as `idle_timeout` on its first reconciliation, so it could never be used a second time.

Useful activity is generation-scoped everywhere it is recorded — `activity_touches` and `activity_sessions` both key on generation — but `sandboxes.last_activity_at` is a single denormalized column. `finish_stop` never clears it when it advances the generation, and `mark_ready` stamps it only through `COALESCE(last_activity_at, now)`, which is a no-op once the column is set. A restarted Sandbox therefore came up holding the activity of the Instance that preceded it, the reconciler compared that timestamp against the Profile's idle timeout, and it drained at once.

Observed against a Profile with `idleSeconds: 60`: generation 1 lived 60.6 s and idle-retired correctly, and generation 2 was drained 244 ms after its own `ready_at` with `termination_reason='idle_timeout'`.

`lifecycle.IdleSince` now bounds the idle window by readiness — an Instance cannot have been idle for longer than it has been ready — and both the drain decision and the wake-up it schedules read that one reference, so they cannot disagree about when a Sandbox is due.

The public `lastActivityAt` is deliberately left alone. Clearing the column would have made a stopped Sandbox stop reporting when it was last used, which is information a caller wants; bounding the comparison instead keeps the field honest and fixes the decision that read it.

## A second deployment on one host seized the first

`secondbox-deploy` could only ever deploy under the Compose project `secondbox`. `runCompose` passed the name as a literal, and `runDockerCompose` scrubs the environment to a Docker-client allowlist that excludes `COMPOSE_PROJECT_NAME`, so there was no way to override it.

Standing up a second deployment on a host that already ran one was therefore destructive rather than additive. Compose matched the running project by name and bound the second deployment to the first's volumes — including `secondbox_postgres-data` — recreated the first's containers against the second's configuration, and, because the deploy path runs `up --remove-orphans`, deleted any container the second service set did not contain.

Deployments now carry an optional `deployment.compose_project_name`, threaded into the `--project-name` argument and validated against the Compose project grammar `^[a-z0-9][a-z0-9_-]{0,62}$`:

```toml
[deployment]
compose_project_name = 'secondbox-staging'
```

Absent means the previous behavior exactly, so every manifest written before this key keeps deploying where it always did. `secondbox-deploy init --mode development` now states the project explicitly, alongside the rest of the deployment identity it already writes.

The flag is the only place this needs to be threaded, because Compose derives every object name from the project and nothing in `deploy/` overrides that: there is no `container_name:` anywhere, the volumes and the `secondbox-backend` network are declared bare, and `--project-name` outranks the `name:` key in `deploy/compose.yml`.

## Install

Download `secondbox` and `secondbox-deploy` for your OS and architecture from the assets below. For Linux amd64:

```sh
mkdir -p ~/.local/bin
curl -fLO https://github.com/SecondStack-AI/SecondBox/releases/download/v0.3.1/secondbox_0.3.1_linux_amd64
curl -fLO https://github.com/SecondStack-AI/SecondBox/releases/download/v0.3.1/secondbox-deploy_0.3.1_linux_amd64
install -m 0755 secondbox_0.3.1_linux_amd64 ~/.local/bin/secondbox
install -m 0755 secondbox-deploy_0.3.1_linux_amd64 ~/.local/bin/secondbox-deploy
```

Install an SDK at the same version:

```sh
npm install @secondstack-ai/secondbox@0.3.1
go get github.com/SecondStack-AI/SecondBox@v0.3.1
```

## Runtime requirements

Executing Sandboxes requires a Linux amd64 Runner host with KVM and TUN, cgroup v2, and a dedicated XFS or Btrfs workspace filesystem with reflink support. Snapshot-resume Profiles additionally require the jailer and a published template. The control plane can run separately; only the Runner needs access to these host facilities.
