# SecondBox v0.26.0

## Deployment boundary

Deployments from v0.14.0 onward update in place and retain their Sandboxes,
Workspaces, Profiles, and authorities. There is no database migration, public
API v1 is unchanged, and the Runner protocol stays at generation 7, so v0.25.0
and v0.26.0 peers interoperate.

Every `[[runners]]` declaration must now state `compute_backend`. Before
running the v0.26.0 deploy CLI, add `compute_backend = 'firecracker'` to each
existing declaration; validation refuses a declaration without it. Guided
installs regenerate their manifest during the update and need no edit.

A same-host Compose Runner now receives the manifest's
`storage_admission_mode`. Earlier releases dropped it, so a same-host Runner
declared with `physical` admission ran with logical admission. After the
update it gates admissions on measured Workspace filesystem use at the
declared thresholds; check the filesystem's headroom before resuming service.

When upgrading from an earlier release, also follow the
[v0.25.0 notes](v0.25.0.md) and the intervening release notes.

## gVisor Runners from secondbox-deploy

`secondbox-deploy` deploys gVisor Runners for Linux amd64 hosts without KVM.
A declaration with `compute_backend = 'gvisor'` carries the `gvisor_*`
settings and none of the Firecracker ones, and `secondbox-deploy
runner-template --backend gvisor` emits it. The deploy CLI takes
`SECONDBOX_GVISOR_MATERIALIZATION_DIGEST` from the verified artifact manifest,
and a release without a gVisor backend refuses the declaration.

- A same-host gVisor Runner renders from
  `deploy/compose.same-host-gvisor-runner.yml`: privileged with the host cgroup
  namespace and a `/dev` bind, with no KVM or TUN device. It runs on the
  deployment network in its own network namespace and dials the control plane
  at `control-plane:9443`, so it does not change the host network namespace
  and its network profile is always 0. Its container runs in
  `secondbox-<project>-gvisor.slice`, so the Instance cgroups of two
  deployments on one host never meet.
- `runner-init` renders the gVisor environment for a remote Runner.
- Validation refuses Runners of different compute backends in one pool and
  more than 63 gVisor Instances per Runner.
- `runner-template` requires `--backend firecracker|gvisor`.

The gVisor runtime guide drops the claim that a Sandbox pins a backend
materialization. Placement and default-image starts use whichever
materialization the home Runner has verified, so an upgrade replaces the
assets while the Runner is stopped.

## Installer and placement

- `secondbox-deploy install` accepts `--sandbox-profile`,
  `--control-reserve-vcpus`, and `--control-reserve-memory-mib` to size a new
  single-host installation for a smaller standard Profile and control
  reserve.
- Sandbox creation, Snapshot clone, and Workspace relocation home a Profile
  that permits attributed execution only on a Runner advertising
  `per-exec-attribution`, and refuse with the retryable
  `home_runner_unavailable` when no Runner in the pool has an attributed
  gateway ([#217](https://github.com/SecondStack-AI/SecondBox/issues/217)).
- The installer post-install smoke gives each smoke Sandbox 15 minutes to
  become ready.

## Release tooling

Releases are cut by pushing a `vVERSION` tag on `main`. `release-tag.yml`
builds the architecture-neutral files once on a GitHub-hosted runner, then
qualifies and stages the amd64 and arm64 artifact sets in parallel on two
self-hosted release runners and dispatches the publisher.

## Bundles

The Firecracker bundles and the standard Profile revisions and spec digests
are unchanged from v0.25.0. Use the released artifact manifest for the exact
bundle, gVisor materialization, image, and Profile identities.

## Distribution

The default lean release qualifies Firecracker and local gVisor and publishes
Linux amd64 OCI images, and the arm64 artifact set publishes the
control-plane, Runner, installer-tools, and microVM-artifact images for Linux
arm64. CLI and deployment binaries ship for Linux and macOS on amd64 and
arm64. It includes the Btrfs-image installer qualification; it does not
include gVisor pod qualification.

The v0.26.0 tag was retracted before publication; install the [v0.26.1](v0.26.1.md) TypeScript SDK and Go module.
