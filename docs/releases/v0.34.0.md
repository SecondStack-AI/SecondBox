# SecondBox v0.34.0

## Deployment boundary

This release adds resource-account compute quotas and migration 0044. Existing
v0.33.0 deployments update in place; no database or Workspace reset is needed.
Public API v1, Runner protocol generation 8, standard Profile revisions and
Firecracker bundles are unchanged. Keep the control plane, Runners, fleet
controller and enrollment tools on the same release. The guided updater's
supported source floor remains v0.14.0; earlier protocol and deployment changes
still require their documented coordinated cutover.

Deploy the new control plane before enabling resource-account requests in an
application. Profiles that require attribution must set
`requireResourceAccount: true`. This is an explicit operator choice; applying a
release does not silently change a Profile's requirement. The requirement on
either the pinned revision or the current Profile revision protects a stopped
Sandbox's next allocation. Its compute size remains pinned to its original
Sandbox resources.

Existing active Sandboxes keep their attribution. Unattributed allocations are
reported separately and are not assigned to an account retroactively. Stop and
restart them with the intended account to adopt account quotas. A failed
Sandbox with an attached Instance remains charged until that Instance is fenced
and detached, including in the existing Tenant and Subject compute totals.

The gVisor address allocator now supports up to 1,024 slots per Runner. Before
starting the new Runner, reserve `169.254.104.0` through `169.254.167.255` and
`198.18.0.0` through `198.18.191.255` against conflicting host and VPN routes or
addresses. Earlier slot mappings remain stable. Address capacity is not a
load-qualified concurrency guarantee; retain explicit compute and host-capacity
limits. See [gVisor runtime](../operations/gvisor-runtime.md).

## Resource-account allowances

Trusted applications can attach a stable account key and complete limits for
active Instances, allocated vCPU and allocated memory to Sandbox create and
start requests. Each limit is a nonnegative integer or explicit `null` for
unlimited. Accounts are scoped to their Tenant and Subject; their keys are
application-owned logical identifiers, not new SecondBox Subjects.

Admission checks the new allocation atomically against the existing Sandbox
allocation rows. Pending starts and compute draining toward stop remain charged.
Reuse of an existing allocation does not transfer its account or charge it
again. A new allocation after release uses the account and allowance supplied
for that admission. Tenant, Subject, Profile and physical-capacity limits still
apply independently.

Applications can read current account usage and its allocations through
`GET /v1/resource-accounts/{key}/usage`. Quota refusal returns a structured
`resource_account_quota_exceeded` response with the constrained axis, current
usage, requested allocation and limit. Go and TypeScript SDKs include these
contracts. Applications must resolve trusted policy themselves; allowing an
untrusted end user to choose arbitrary account keys or limits bypasses the
application's own policy.

## Lifecycle retries

A retry of an admitted create or start may carry a new remaining capacity-wait
budget or freshly resolved account limits. It replays the original operation
and preserves that operation's accepted deadline and allocation. The account
key, selected execution image and other request identity must still match.
An attributed failed Instance that remains attached can recover using its
existing charge; a detached or never-placed failure must pass a fresh admission.

## Distribution and bundle identity

The release retains both Linux amd64 and arm64 runtime artifact sets. gVisor
images and artifacts remain amd64-only, as does the AWS worker reference.
CLI, deploy, fleet-controller and fleet-enrollment binaries ship for Linux and
macOS on amd64 and arm64; fleet tools are installed separately by their operator.

The Firecracker bundles remain those documented by v0.33.0/v0.32.2/v0.31.0.
Use this release's published artifact manifests and checksums for all binary,
container and gVisor materialization identities. SDK coordinates are
`@secondstack-ai/secondbox@0.34.0` and
`github.com/SecondStack-AI/SecondBox@v0.34.0`.
