# SecondBox v0.32.0

## Deployment boundary

Deployments from v0.14.0 onward update in place. This release adds migrations
0039–0043 and changes the Runner protocol from generation 7 to generation 8.
Public API v1, guest protocol generation 1 and standard Profile revisions remain
unchanged. Generation 7 and generation 8 control planes and Runners cannot
connect to each other.

Finish pending relocations, stop Sandboxes and stop every Runner before updating.
Back up PostgreSQL and each Runner storage root. Update the control plane, all
Runners and any fleet tools together, then confirm enrollment and a start on
each served Profile before reopening service. Use the verified artifact
manifest for the selected architecture to materialize and pin execution assets.

Archive tiering is explicitly configured and does not enable itself on update.
When enabled, preserve the archive bucket, configuration and credentials as part
of the deployment's recovery boundary. Rollback must restore matching database,
Runner storage and object-store ownership; an older database alone does not
recover archived or relocated Workspace authority. See
[storage-tiering operations](../operations/workspace-storage-tiering.md).

## Workspace storage tiers

- Stopped, Snapshot-free Workspaces can move directly between their Runner and
  S3 using short-lived grants. The control plane records the authoritative
  generation and verified descriptor without receiving image bytes.
- A start restores an archived Workspace onto a compatible Runner. Logical
  image and archive checksums are verified before committing its new home.
  Failed export retains the local authority; failed restore retains the
  authoritative archive.
- Per-Profile cold-age and physical-pressure policies release local storage.
  A pending start can offload from a full or draining connected home while
  preserving the original start Operation and capacity-wait deadline.
- Lost restore targets are abandoned after a bound and excluded until exact
  orphan cleanup succeeds. Durable replay tombstones prevent delayed imports
  or old cleanup commands from modifying a later home.
- Sandbox observations expose residency and compressed archive bytes. Mounted
  execution, writable local disks and Snapshots retain their existing semantics.

Configure incomplete multipart-upload cleanup on the bucket. Disabling tiering
requires restoring archived Workspaces and completing outstanding transfer and
object cleanup; startup refuses a configuration that would strand them.

## Elastic AWS workers

The reference deployment uses EC2 Auto Scaling, an XFS reflink data volume per
worker and S3 archives. The fleet controller reads durable demand, provisions
workers, enrolls individual Runner and gateway identities and evacuates local
Workspaces before retirement and exact-instance termination.

Worker certificates renew against fresh cloud ownership proof while retaining
their original keys and identities. New TLS handshakes reload renewed leaves;
established streams continue. Retired identities cannot enroll again. Fleet
administration and signing keys stay within the trusted control-plane boundary.

Bootstrap failures remain visible without stopping reconciliation of healthy
workers. Scale-in protects restoring Workspaces and deletes only detached data
volumes covered by a committed retirement receipt. Unexpected-loss volumes
remain for operator recovery. The reference uses on-demand workers; a local-only
generation still requires its Runner disk for recovery after node loss.

See [AWS workers](../../deploy/aws-fleet/README.md) for explicit capacity,
networking, enrollment and production configuration. Optional destructive expiry
exists for disposable qualification runs and is disabled by default.

## Storage-pressure and gVisor fixes

Runners denied new work by storage pressure remain connected for cleanup and
require measured recovery before placement. Failed Workspace creates without a
durable receipt are recorded correctly. gVisor mount supervisors reap adopted
processes, and flat-root verification ignores host SELinux labels. Custom
materializations whose digests included SELinux labels require rebuilding.

## Distribution

The default release qualifies Firecracker, local gVisor and the Btrfs-image
installer. It publishes Linux amd64 images for the control plane, Runner,
installer tools, microVM artifacts, gVisor Runner and gVisor artifacts. The
arm64 set publishes the control plane, Runner, installer tools and microVM
artifacts. gVisor pod qualification is outside the default release tier.

CLI, deploy, fleet-controller and fleet-enrollment binaries ship for Linux and
macOS on amd64 and arm64. The guided installer still installs only the CLI and
deploy tool. Fleet tools are installed separately by their operator.

Install the TypeScript SDK with `npm install @secondstack-ai/secondbox@0.32.0`.
The Go module is `github.com/SecondStack-AI/SecondBox@v0.32.0`.

## Bundle identity

Firecracker execution bundles are retained from v0.31.0. This release changes
the host Runner protocol and storage control, with no guest-agent or guest
protocol change. The amd64 `secondbox-0.31.0` bundle manifest remains
`sha256:d7e570672f872781798f96f4026f1f068254ede3604bd0f9bc540111aab084cc`;
the arm64 bundle remains the one described by the v0.31.0 artifact manifest.
See the [v0.31.0 bundle notes](v0.31.0.md#bundle-identity) for component identities
and the architecture-specific trust-store boundary.

Use the new release's verified artifact manifest for container, binary and
gVisor materialization digests. Retaining a guest bundle does not make
generation 7 host Runners compatible with this control plane.
