# SecondBox v0.33.0

## Deployment boundary

This release removes execution-image hashing from Runner restarts and from the
boot of pre-baked AWS Code workers. Public API v1, Runner protocol generation 8,
database migrations, standard Profile revisions and the Firecracker bundles are
unchanged from v0.32.5. Existing v0.32.x deployments update in place. Keep the
control plane, all Runners, fleet controller and enrollment tools on the same
build. The guided updater's supported source floor remains v0.14.0.

Firecracker and gVisor Runners require
`SECONDBOX_RUNNER_EXECUTION_IMAGE_VERIFICATION_ROOT`, a Runner-private directory
outside the execution-image cache. `secondbox-deploy` renders it for managed
Runners, and the same-host Compose files, the AWS worker Compose file and the
gVisor pod set it. Remote, Kubernetes and hand-written Runner environments must
add it before the update. The first start after the update verifies each cached
image once in the background.

A pre-baked AWS fleet needs a new AMI build, which now also produces a worker
data snapshot. Deploy the fleet template with both `WorkerAMI` and the new
`PrebakedWorkerDataSnapshot`. A v0.32.x AMI has no matching data snapshot and
does not work with this template. Download-mode fleets are unaffected.

Cut a pre-baked fleet over at zero workers:

1. Set the controller's `minimumNodes` to zero, stop new work on the pool's
   Profiles and let running Sandboxes stop, then let the controller evacuate and
   retire every worker. Evacuation archives each stopped Workspace; active
   assignments, retained Snapshots and pending mutations block it. Wait until
   the group has no instances and only receipted volumes were deleted. Keep any unreceipted retained volume for
   operator recovery; this release's pre-baked bootstrap refuses it, because it
   carries no data-snapshot bundle marker.
2. Pause fleet reconciliation and update the control plane, fleet controller and
   enrollment tools to this release.
3. Build the AMI and data snapshot with this release's bundle, then update the
   template with `WorkerAMI`, `PrebakedWorkerDataSnapshot`, and the bundle's
   SHA256 in both `WorkerBundleSHA256` and `PrebakedWorkerBundleSHA256`, with
   the bundle location pinned to the same object.
4. Resume reconciliation. Archived Workspaces restore onto new workers on their
   next start.

Upgrades from v0.31.x or earlier must follow the complete
[v0.32.1 coordinated cutover procedure](https://github.com/SecondStack-AI/SecondBox/blob/v0.33.0/docs/releases/v0.32.1.md#deployment-boundary).

## Execution-image verification records

A Runner verifies each execution-image bundle once and then admits later starts
on the filesystem identity of every verified file. It now keeps that proof in
records under its private verification root, so a Runner or image-fetcher
restart no longer adds full hashing to the first start of each cached image.
After a restart the Runner verifies prepared and cached images in the
background, most recently used first. The image fetcher no longer re-hashes a
cache hit: only verified bundles enter the cache, and the Runner verifies before
every launch.

The Runner trusts only a record root and record files it owns with owner-only
access, opened without following links. A record binds each file on the bundle
directory's filesystem by inode, size and modification and change times,
without its device number, so a reboot that renumbers block devices or a data
volume cloned from a snapshot keeps it. A file on another filesystem keeps its
exact device. Any metadata change forces one full re-verification.

`secondbox-runner -record-execution-image-verifications` verifies and records
every cached bundle once and exits. It fails when any bundle fails, lacks a file,
or the cache is empty. Worker image builds use it.

## Ready pre-baked AWS workers

The AMI build attaches a blank 64 GiB disk to its builder and prepares it as the
worker data snapshot: a reflink XFS filesystem with the base artifacts, the
execution-image cache owned by the image fetcher and the Runner's verification
records, written by the bundle's own Runner image under the worker's container
paths. The AMI holds only the root disk and no longer carries the compressed
execution cache. The build creates the data snapshot before the image and
records it as `dataSnapshotId`. The provisioning role additionally needs
`ec2:CreateSnapshot` and `ec2:DescribeSnapshots` on its owned builder volume and
snapshot.

Each worker's data volume is created from that snapshot at `WorkspaceGiB`, and
both worker volumes initialize from their snapshots at a provisioned 300 MiB/s,
which EBS bills per restored GiB. Bootstrap claims a fresh volume, grows its
filesystem and writes the fleet marker. It copies, stages and hashes nothing,
and it does not change cache ownership, which would invalidate the records. The
volume keeps the bundle marker of its snapshot; every pre-baked bootstrap
refuses a volume of another bundle, retained volumes included. The Runner still
verifies the small base root before it reports ready.

On the staging Code pool, a fresh Sandbox on a new worker became ready 88
seconds after admission, against 645 seconds with the v0.32.5 pre-baked AMI.
The Runner connected 9 seconds after worker enrollment instead of 472 seconds.
A worker whose Code image is not in its data snapshot downloads and verifies it
on first use, so rebuild the AMI and snapshot when the image changes.

See [AWS workers](https://github.com/SecondStack-AI/SecondBox/blob/v0.33.0/deploy/aws-fleet/README.md)
for the build, template and bootstrap contract.

## Distribution and bundle identity

Both amd64 and arm64 runtime artifact sets are retained. The gVisor images and
artifacts remain amd64-only, as does the AWS worker reference. CLI, deploy,
fleet-controller and fleet-enrollment binaries ship for Linux/macOS on
amd64/arm64; fleet tools are installed separately by their operator.

The Firecracker bundles remain those documented by v0.32.2/v0.31.0. Use this
release's published artifact manifests and checksums for all binary, container
and gVisor materialization identities. SDK coordinates are
`@secondstack-ai/secondbox@0.33.0` and
`github.com/SecondStack-AI/SecondBox@v0.33.0`.
