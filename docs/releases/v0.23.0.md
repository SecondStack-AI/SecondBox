# SecondBox v0.23.0

## Deployment boundary

Deployments from v0.14.0 onward update in place and retain their Sandboxes,
Workspaces, Profiles, and authorities. This release has no database migration.
It keeps public API v1 and the Runner protocol window `[6,6]`. The signed
execution bundle, trust anchor, and standard Profile revisions are unchanged
from v0.22.0, and peers using v0.22.0 and v0.23.0 can connect in either update
order. When upgrading from an earlier release, also follow the
[v0.22.0 notes](v0.22.0.md) and the intervening release notes.

## Linux arm64 Runner hosts

A Linux arm64 host with KVM and 4K pages can run the Firecracker Runner with
arm64 guests ([#201](https://github.com/SecondStack-AI/SecondBox/pull/201)).
A release carries one guest architecture. The published v0.23.0 release is the
amd64 release; an arm64 deployment stages its own release from this tag with
`RELEASE_GUEST_ARCHITECTURE=arm64` and `RELEASE_IMAGE_PLATFORMS=linux/arm64`.

- The guest kernel, microVM bundle, Runner image, and client execution-image
  builder take an explicit `amd64` or `arm64` architecture. An arm64 Debian
  image definition builds the standard guest rootfs.
- Standard Profiles of an arm64 release bind the new `standard-arm64`
  RunnerPool. Their revision digests differ from the amd64 Profiles of the same
  name.
- An arm64 release is qualified by `linux-arm64` scenario evidence. It carries
  no gVisor artifacts and no installer qualification evidence: gVisor and the
  guided single-host installer remain amd64-only, and the installer refuses an
  arm64 release.
- `init --mode development`, `just test-scenario`, and `just prepare-stress`
  follow the host architecture.

Known limits on arm64: the release publisher cannot publish an arm64 release,
Runners use CPU template `None`, and the snapshot-resume host fingerprint reads
the first CPU only, so it does not describe every core of a mixed-core host.

## Changes for amd64 build automation

Published amd64 artifacts keep their format and identities. Automation that
builds images from this repository must change:

- `scripts/build-client-execution-image.sh` requires
  `SECONDBOX_CLIENT_IMAGE_ARCHITECTURE`. The microVM kernel, rootfs-source, and
  bundle builders require `SECONDBOX_RUNNER_MICROVM_ARCHITECTURE`.
- A prepared rootfs source built before this release records no architecture
  and must be rebuilt.
- The Go helpers `standardresources.Documents`, `ProfileLineage`, and
  `DevelopmentProfileLineage`, and
  `releasecontract.QualificationEvidence.ValidateForRelease`, take the guest
  architecture.
- Release verification requires scenario qualification evidence from a host of
  the release guest architecture.

## Fixes

- `BUILD_KERNEL=true` microVM builds no longer compile the pinned kernel a
  second time under `fakeroot`.
- The development tenancy bootstrap no longer writes its request bodies over
  the CLI session files of the same name.

## Firecracker bundle and trust anchor

The release retains the signed `secondbox-0.17.0` Firecracker bundle and the
v0.12.0 RSA trust anchor. The public key's canonical DER SHA-256 remains:

```text
59c127f459b8c93ca422f2f6c5bd43ff1e17d50309a262b7aff1b07bf59a5ced
```

Standard Profile revisions and their spec digests remain unchanged from
v0.19.0. Use the released artifact manifest for exact bundle, image, and Profile
identities.

## Distribution

The default lean release qualifies Firecracker and local gVisor and publishes
Linux amd64 OCI images. CLI and deployment binaries ship for Linux and macOS
on amd64 and arm64. It includes the Btrfs-image installer qualification; it
does not include gVisor pod qualification or an arm64 control-plane image.

Install the TypeScript SDK with `npm install @secondstack-ai/secondbox@0.23.0`.
The Go module is `github.com/SecondStack-AI/SecondBox@v0.23.0`.
